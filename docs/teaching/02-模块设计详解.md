# 教学文档 02 · 逐模块功能与设计详解

> 本文按模块拆解代码，讲清每个模块**做什么、关键函数/常量在哪、为什么这样设计、有什么取舍**。

## A. 编排层（LangGraph 主图）

**位置**：`engine/orchestration/main_graph.py`、`state.py`

### 做什么
把一次学习交互建模成一张**有状态的图**（StateGraph），而不是一条顺序调用链。这是 ADR-0001 的核心决定：用真正的 LangGraph 状态图承载分支、循环、条件路由。

### 主图流程
```
personalize_opener → router → {qa | training | capstone}
   → (仅 qa) learner_update → closing_advice → END
```

### 关键 API
```python
build_main_graph(
    retriever,              # 检索器（领域无关注入）
    llm=None,               # LLM 客户端
    learner_model=None,     # 学习者模型服务
    training_service=None,  # 训练服务
    checkpointer=None,      # LangGraph 检查点（可选，支持恢复）
    compile_graph=True,     # 是否编译成可执行图
)
```

### 设计要点（面试常问）
- **依赖注入**：主图不 `import` 任何具体课程内容，只接收抽象依赖。这就是"引擎领域无关"铁律在代码层的落地——换课只换 CoursePack，图不动。
- **router 节点**：根据用户意图把请求分派到 qa / training / capstone 三条支线，体现"一个图统一编排多种学习模式"。
- **state 是单一事实源**：`state.py` 定义图状态（TypedDict 风格），数据在节点间靠 state 传递，节点是纯函数式的"读 state → 产出 state 增量"。这让每个节点可独立单测。

### 取舍
- 用图而非链，换来了**可视化、可回放、可条件循环**（如 QA 的重试环），代价是学习曲线和一点样板代码。项目认为对"Agentic"产品这个代价值得（ADR-0004 把子图分层，进一步控制复杂度）。

## B. QA 子图（Agentic RAG 的核心）

**位置**：`engine/orchestration/subgraphs/qa_graph.py`、`engine/retrieval.py`

### 流程
```
retrieve → evidence_check → answer → review → final
              │
              ├─(证据不足且可重试)→ query_rewrite →(回)→ retrieve
              └─(证据不足且到上限)→ refuse
```

### 关键常量与路由
```python
STRONG_EVIDENCE_THRESHOLD = 0.75
WEAK_EVIDENCE_THRESHOLD   = 0.35

def route_after_evidence(state):
    if 证据充分:                    return "answer"
    if retry_count < max_retry:     return "query_rewrite"  # 改写查询再检索
    else:                           return "refuse"          # 诚实拒答
```

### 设计要点
- **evidence_check 是"诚实"铁律的守门员**：不是检索到就答，而是先给证据打分。分数不够先尝试**改写查询重检索**（query_rewrite 循环），仍不行就 `refuse`。拒答是一个**特性**，不是失败。
- **review 节点**：答完再复核"答案是否只用了给定证据、引用是否真实存在"，防止 LLM 幻觉出资料里没有的引用/页码。
- **citations / sources**：answer 产出结构化引用 `[n]`，映射到具体切片，前端可点击定位回原文。

### 检索器 `retrieval.py`
- 查 Chroma（collection = `pack_<id>`，余弦距离），取 top-k 切片。
- embedding 走 Ark 多模态（文本+图统一向量，2048 维）；无 key 时用 Mock。

### 取舍
- 证据阈值是**硬编码常量**——这是允许的，因为它是引擎的**通用检索质量策略**，不含任何课程内容，不违反领域无关铁律。可讲的点：阈值该不该做成课程包可配？当前选择是"通用默认值 + 保持引擎简单"。

## C. 学习者模型（掌握度）

**位置**：`engine/learner_model/service.py`，业务表 `mastery`

### 做什么
维护"每个学生 × 每个知识点"的掌握度状态，作为个性化与洞察的数据基座。

### 关键常量与规则
```python
KNOWN_SCORE_THRESHOLD = 0.8   # ≥ 视为"已掌握"
FUZZY_SCORE_THRESHOLD = 0.4   # ≥ 视为"模糊"
```

| 掌握度来源 | 可达上限 |
|---|---|
| QA 提问接触知识点 | 最高 FUZZY（模糊） |
| 训练题判分正确 | 可达 KNOWN（已掌握） |
| 讲师人工订正（INSTRUCTOR_CORRECTED） | 永不被系统覆盖 |

### 设计要点
- **来源决定上限**：这是整个学习闭环的诚实性核心。"我问过一个问题"不等于"我掌握了"，所以 QA 只能提到模糊；只有**做对训练题**这种可验证的行为才能标"已掌握"。
- **人工订正最高优先级**：讲师的判断压过一切自动推断，`INSTRUCTOR_CORRECTED` 状态锁定，系统的自动更新逻辑必须跳过它。

### 取舍
- 用离散状态（未接触 / 模糊 / 已掌握 / 讲师订正）而非纯连续分数，便于讲师看板展示和学生理解，代价是丢失一部分细粒度。

## D. 个性化与主动建议（装饰器）

**位置**：`engine/orchestration/decorators/personalization.py`

### 做什么
- `personalize_opener`：进入主图第一步，读学习者模型生成**个性化开场白**（例如"你上次在 RAG 检索这块还比较模糊，这次我们重点看…"）。
- `closing_advice`：交互结尾**主动推荐下一步**（去做某个训练、或看某个薄弱知识点）。

### 设计要点
- 这两个是**图节点级的装饰**，把"个性化"和"主动性"从答案生成里解耦出来。答案负责"答对"，个性化节点负责"针对这个学生说话"。
- 依赖学习者模型（B 块）的数据，所以它是 B 块的消费者。

## E. 训练闭环

**位置**：`engine/training/service.py`、`engine/training/seed.py`、`engine/orchestration/subgraphs/training_graph.py`，业务表 `question_bank` / `exercise_attempt`

### 做什么
出题 → 学生作答 → 判分 → **回写掌握度**（这是唯一能把知识点提到"已掌握"的路径）。

### 关键组成
- `training_graph.py`：训练支线的子图（router 分派到这里）。
- `service.py`：题库读取、判分、掌握度回写。
- `seed.py`：题库种子数据装载。
- 题目来源：ingestion 阶段 AI 抽取的**候选题目**（status=candidate），经讲师审核后进入正式题库。

### 设计要点
- 训练是"掌握度可信度"的来源。把判分和掌握度回写放在一起，保证"做对 → 提升"的因果闭环。
- 候选题目要讲师审核才生效，避免 AI 抽取的低质量题直接推给学生。

## F. 结课项目陪练

**位置**：`engine/capstone/service.py`，业务表 `capstone_project` / `milestone_progress`

### 做什么
把结课项目拆成**里程碑**，逐里程碑引导学生推进，记录每个里程碑的进度。直接服务北极星指标（完成结课项目的学员比例）。

### 设计要点
- 里程碑式（milestone）结构：项目不是一次性交付，而是分阶段陪练，每阶段有明确产出与进度记录。
- 通过 router 从主图进入 capstone 支线。

## T. 教学洞察

**位置**：`engine/insights/service.py`、`routes/insights.py`

### 做什么
面向讲师聚合：
- 班级整体**掌握度分布**；
- **高频提问**；
- 被系统**拒答的问题**（直接暴露课程资料的盲区——哪里没资料，学生一问就被 refuse）；
- **候选知识点 / 候选题目审核**（approve 后才生效）。

### 设计要点
- "拒答问题聚合"是一个巧妙的产品设计：refuse 不只是对学生诚实，其日志反过来成了**讲师补资料的指路灯**。
- 所有 insights 接口 + 训练候选接口都要过 `require_teacher`（后端强制）。

## 入口层：Routes（HTTP → 引擎）

**位置**：`routes/`（chat / auth / training / capstone / insights / archive / courses / admin / health / version）

### 关键端点
| 端点 | 说明 |
|---|---|
| `POST /api/chat` | 同步问答，走完整主图 |
| `POST /api/chat/stream` | SSE 流式，推**节点级真实进度** + 最终 review 后的 final 事件 |
| `auth/*` | 注册/登录，签发 HMAC token |
| `training/*` | 出题/作答/判分，候选审核（部分 require_teacher） |
| `capstone/*` | 结课项目里程碑 |
| `insights/*` | 教学洞察（全部 require_teacher） |
| `archive/*` | 会话归档 |
| `courses/*` | 课程/课程包 |

### 鉴权工具
- `resolve_learner_id(token, body)`：token 身份优先于 body；游客 → `demo_user`。
- `require_teacher`：讲师专属守卫。

### 设计要点
- Route 层**薄**：负责解析请求、鉴权、调用 engine、持久化、组装响应。业务逻辑在 engine，不在 route。这保证 engine 可脱离 HTTP 单测。

## 内容注入层：Course Pack

**位置**：`course_pack/`，约定目录 `data/course_packs/<id>/`

### 做什么
把课程特定内容（课程元信息、知识点体系、题目、里程碑定义）从磁盘目录加载，注入给领域无关的 engine。这是 ADR-0002/0006 的落地。

### 设计要点（本项目最重要的架构点）
- **加新课 = 放新目录，引擎零改动。** 这条要能脱口而出。
- 首个课程包 `ai_agent`：内容是 LangChain / LangGraph / MCP / RAG。
- 内容是**数据驱动**的（ADR-0006），不是代码里的 if-else。

## 摄取层：Ingestion

**位置**：`ingestion/`

### 流水线
```
HTML / MD / PDF / 代码
 → parse(按类型) → chunk(size=800, overlap=120)
 → Ark 多模态 embedding → Chroma(collection=pack_<id>, cosine)
 → AI 抽取候选 taxonomy + 候选题目(status=candidate) → 讲师审核
```

### 设计要点
- **切片参数** size=800 / overlap=120：重叠是为了避免答案跨切片边界被切断，检索时能召回完整上下文。
- **多模态 embedding**：PPT/PDF 里的图也能被向量化检索（ADR-0003），这是选 Ark 多模态而非纯文本 embedding 的理由。
- **AI 抽取 + 人工审核**：AI 提效，讲师把关质量，候选态是这个协作模式的关键设计。

## LLM / Embedding 客户端（可替换）

**位置**：`llm/`

```python
get_llm_client()        # llm_provider=="openai_compatible" → ArkChatClient，否则 MockLLMClient
get_embedding_client()  # embedding_provider=="ark_multimodal" → ArkMultimodalEmbeddingClient，否则 Mock
```

### 设计要点
- **工厂 + 接口**：engine 只依赖抽象客户端接口，不依赖 Ark。无 key 时自动回退 Mock，让**测试和本地开发无需真实 key**（154 passed 里绝大多数不碰网络）。
- 这是"可测试性优先"的典型设计，也是面试可讲的依赖倒置例子。

## 持久化层：两套 DB

**位置**：`persistence/`、`repositories/`、`models/`

| | 业务库(SQLModel) | 脚手架库(sqlite3 + .sql) |
|---|---|---|
| 表 | learner, learner_auth, learner_profile, mastery, milestone_progress, capstone_project, exercise_attempt, question_bank, qa_history | courses, course_chunks, conversations, messages, traces, trace_events, eval_cases |

### 设计要点
- 业务实体用 ORM（类型安全、关系建模，ADR-0005）；平台/可观测数据（trace/eval/会话）用轻量 sqlite3 + 显式 SQL 迁移。
- `traces` / `trace_events`：记录每次图执行的节点轨迹，支撑前端 trace 可视化和"诚实流式"的进度回放。

## 前端架构

**位置**：`scaffold/apps/web/src/`

### Provider 链
```
Theme → Auth → Role → Router → Preview
```
每层只管一件事：主题、登录态、角色、路由、资料预览浮层。

### 路由与角色
- 路由文件：`routes/`（student / teacher / training / capstone / courses / course-detail / archive / profile / login）。
- `RequireRole` 守卫：学生看不到讲师页。**仅 UI 层**——真权限在后端。
- `React.lazy` 代码分割：按路由懒加载。

### 数据层（MVP 锁定轻量方案）
- `api/client.ts`：真实 fetch + SSE，**不引 TanStack Query**。
- 按面拆 `api/{chat,insights,courses,training,capstone,archive,auth}.ts`；`api/types.ts` 与后端 schema **逐字段对齐**（snake_case，不做命名转换）。
- hooks：`useChat / useInsights / useTraining / useCapstone / useArchive / useCandidates / useMetrics` —— 每个数据面一个 hook，封装 loading/empty/error/success 四态。

### streamChat（诚实流式）
- `streamChat` 消费 SSE 节点级进度；SSE 不可用则回退同步 `postChat`。
- 前端不做"假打字机"，进度来自后端真实节点事件。

### 引用点击链（体现前后端协作）
```
AnswerText 渲染 [n]
 → handleCitationClick(n)
 → 定位 sourceRefs
 → 滚动到 MaterialPreview 对应锚点
```

### 设计纪律（taste-skill，见 docs/FRONTEND.md）
- **单一 accent 全站锁定** + **单一圆角** `var(--radius)`；组件禁写死 hex，一律 `var(--color-*)` token。
- 图标只用 **Phosphor** 单库，禁手搓 SVG。
- 动效只保留有意义的；`MOTION_INTENSITY>3` 必须带 `prefers-reduced-motion` 回退。
- **四态纪律**：每个数据面都要有 loading（骨架屏匹配最终布局，禁通用 spinner）/ empty / error（可读+重试）/ success。
- 文案禁 em-dash；按钮/表单满足 WCAG AA 对比度。
