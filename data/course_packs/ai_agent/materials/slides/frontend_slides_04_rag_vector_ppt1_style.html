Problem Framing03 / 24

PROBLEM

大模型的知识局限

LLM 擅长推理与生成，但不等于拥有可验证、实时、企业私域的知识。

幻觉问题

模型基于概率生成，如果缺少事实来源，可能一本正经地编造论文、数字或结论。

01

时效性问题

训练数据存在截止日期，新闻、政策、价格、最新论文等信息天然滞后。

02

领域知识缺失

公司内部文档、产品 API、业务流程、员工手册通常不在训练语料中。

03
RAG 的核心目标：让 LLM 从“闭卷考试”变成“带资料作答”。

Strategy Choice05 / 24

COMPARE

RAG vs Fine-tuning

两者不是替代关系：RAG 解决“知识注入”，Fine-tuning 更适合“行为塑形”。

RAG

  • 知识更新快：替换文档即可
  • 可追溯：回答可附引用来源
  • 适合企业知识库、客服、搜索问答
  • 挑战：检索质量和上下文组织

Fine-tuning

  • 稳定改变模型风格与任务模式
  • 适合格式化输出、领域术语、分类策略
  • 更新成本更高，需要训练与评估闭环
  • 挑战：不适合频繁注入事实知识
实践建议：知识变化频繁先选 RAG；输出行为不稳定再考虑微调。
Lexical Retrieval06 / 24

BM25

关键词检索

BM25 是搜索系统的经典基线，适合精准词匹配、型号、代码、专有名词。

  • TF：词在文档中出现越多，相关性越高
  • IDF：越稀有的词，区分度越强
  • Length Norm：避免长文档天然占优
  • 弱点：不理解语义同义表达

Similarity08 / 24

SIMILARITY

向量相似度计算

相似度函数决定“哪个文档更接近查询”，常见选择包括 Cosine、Dot Product 与 Euclidean Distance。

Cosine Similarity

关注向量方向，常用于归一化文本向量；适合比较语义角度。

cos

Dot Product

同时受方向与长度影响，常见于向量数据库和模型服务的默认打分。

dot

Euclidean

计算空间距离，更直观但在高维语义向量中不总是最佳选择。

L2
score(q, d) = cosine(embedding(q), embedding(d))
ANN Index09 / 24

ANN

向量索引：近似检索

全量扫描成本过高，ANN 用“近似但足够好”的方法换取低延迟。

  • HNSW：图结构，多用于低延迟在线检索
  • IVF：聚类倒排，适合大规模向量召回
  • PQ：压缩向量，降低存储与内存成本
  • 核心权衡：Recall、Latency、Cost

Chunking11 / 24

CHUNKING

文档分块策略

分块质量直接影响召回质量：块太小丢上下文，块太大引入噪声。

固定长度

实现简单，适合基线；缺点是可能切断语义结构。

01

语义分块

按标题、段落、句子边界切分，保持自然语义单元。

02

Overlap

相邻块保留重叠窗口，降低边界信息丢失。

03

Metadata

保留标题、路径、时间、权限等字段，支持过滤与加权。

04
经验值：先从 300–800 tokens + 10%–20% overlap 开始，再用评估集调参。
Chroma12 / 24

VECTOR DB

Chroma 向量数据库

Chroma 适合教学与原型验证，接口直接，能快速演示 collection、add、query、update。

  • Collection：向量、文本、元数据的逻辑集合
  • Add：写入 documents、embeddings、metadata
  • Query：向量相似度检索 Top-K
  • Update/Delete：支持知识库迭代维护

import chromadb

client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_or_create_collection("course_docs")

collection.add(
    ids=["doc-1"],
    documents=["RAG means retrieval augmented generation"],
    metadatas=[{"source": "lesson-04"}],
)

results = collection.query(
    query_texts=["what is RAG"],
    n_results=3,
)

LangChain RAG15 / 24

IMPLEMENTATION

LangChain RAG 完整实现

用 Runnable 组合加载、检索、格式化上下文与生成回答，形成最小可运行链路。

rag_chain.py
from langchain_core.runnables import RunnablePassthrough
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_chroma import Chroma

retriever = Chroma(
    persist_directory="./chroma_db",
    embedding_function=OpenAIEmbeddings(),
).as_retriever(search_kwargs={"k": 5})

prompt = ChatPromptTemplate.from_template(
    "Answer from context only.\nContext:{context}\nQuestion:{question}"
)

rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | ChatOpenAI(model="gpt-4o-mini")
)
print(rag_chain.invoke("什么是 RAG？"))

Optimization17 / 24

RETRIEVAL QUALITY

检索优化策略

RAG 质量差时，不要只怪模型，优先拆解是召回、排序、上下文还是生成出了问题。

Query Rewrite

将口语化问题改写为适合检索的查询，补充同义词和关键实体。

01

Multi-Query

从多个角度生成查询，提高召回覆盖面，但要控制成本。

02

Rerank

用 cross-encoder 或 LLM 对候选片段重新排序，提升 Top-K 精度。

03

Context Compress

压缩或过滤无关片段，降低上下文噪声。

04
诊断顺序：先看是否召回正确文档，再看排序是否靠前，最后看 Prompt 是否要求基于证据回答。
Evaluation18 / 24

EVALUATION

RAG 效果评估

需要同时评估检索与生成：答案看起来流畅，不代表证据正确。

  • Context Precision：召回片段中有多少是有用证据
  • Context Recall：必要证据是否被召回
  • Faithfulness：回答是否忠实于上下文
  • Answer Relevancy：回答是否真正解决问题
ragas_eval.py
# pip install ragas
from ragas.metrics import faithfulness, answer_relevancy

result = evaluate(
    dataset,
    metrics=[
        faithfulness,
        answer_relevancy,
        context_precision,
        context_recall,
    ],
)
print(result)

上线 RAG 的关键不是“能跑 demo”，而是可观测、可回滚、可治理、可持续评估。

数据治理

索引运维

02

质量闭环

03

安全合规

04
生产化检查：回答是否可追溯？召回是否受权限控制？Embedding 与索引是否能平滑升级？
