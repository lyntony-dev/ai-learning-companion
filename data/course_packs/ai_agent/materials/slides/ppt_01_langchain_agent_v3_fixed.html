CONCEPT · 概念解释

先理解：装饰器 @tool 到底是什么？

🏷️ 比喻：贴标签
把 @tool 想象成一张标签贴纸：
把它贴在函数头上，Python 就知道"这个函数是给 Agent 用的工具"。
函数本身没变，只是多了一个身份。
对比：普通函数 vs 工具函数
# 普通函数：任何 Python 代码都能调用 def get_weather(city): return f"{city}今天晴" # 加上 @tool：LangChain 能识别它 @tool def get_weather(city: str) -> str: """获取城市天气""" return f"{city}今天晴"
💡 @tool 帮你做了什么？
1. 提取函数名 → 变成工具名
2. 读取参数类型 → 告诉 LLM 该传什么
3. 读取 docstring → 告诉 LLM 工具做什么
4. 注册到工具列表 → Agent 能找到它

如果没有 @tool，你要手写几十行代码做这些事
📖 类型注解也很关键
city: str 告诉 LLM：要传字符串
-> str 告诉 LLM：会返回字符串

⚠️ 不写类型注解：LLM 无法正确调用工具！
✓ 写了类型注解：LLM 精确知道参数格式
✋ 你只需要记住
写 Agent 工具时，始终按这三步：① 写 @tool、② 加类型注解 (x: str) -> str、③ 写清楚 docstring 说明工具用途。剩下的 LangChain 帮你搞定。
Speaker Notes
核心要点
  • 装饰器是 Python 中级语法，学两周不可能懂，必须用比喻
  • "贴标签"比喻最容易接受——不需要解释函数是一等对象
  • 类型注解和 docstring 是 Agent 工具能被 LLM 识别的关键
  • 下一页看实际代码，学生已经有了心理准备
教学建议
可以在白板画：函数 = 快递盒，@tool = 贴运单，LangChain = 快递系统。让学生理解装饰器不改变函数本身，只是让系统"能找到它"。

STEP 02 · TOOLS

工具定义

@tool 装饰器（推荐）
最简单的工具定义方式。函数名即工具名，docstring 即工具描述，类型注解即参数 schema。
BaseTool 类
适合复杂逻辑。继承 BaseTool，实现 _run() 方法，可定义内部状态。
关键点
工具的 name 和 description 是 LLM 决定是否调用的依据，必须清晰准确。
from langchain_core.tools import tool # 方式一：@tool 装饰器 @tool def get_weather(city: str) -> str: """获取指定城市的天气信息。 Args: city: 城市名称，如"北京"、"上海" """ # 实际调用天气 API return f"{city}今天晴，25°C" # 方式二：BaseTool 类 from langchain_core.tools import BaseTool class CalculatorTool(BaseTool): name: str = "calculator" description: str = "数学计算器" def _run(self, expression: str) -> str: return str(eval(expression))

STEP 04 · BIND TOOLS

绑定工具 bind_tools()

LLM 如何知道该调用哪个工具？
bind_tools() 将每个工具的 name + description + 参数 schema 转成 JSON Schema，注入到 LLM 的 System Prompt 中。LLM 根据用户意图语义匹配最合适的工具。
工具选择三要素
  • name：工具名，如 get_weather
  • description：docstring 描述，LLM 据此判断是否匹配
  • args_schema：参数类型 + 说明，LLM 据此提取参数
用户问"北京天气" → LLM 匹配 get_weather → 返回 tool_calls
LLM 的角色
LLM 不执行工具，只返回 tool_calls（工具名 + 参数 JSON）。你的代码负责执行工具并将结果回传给 LLM。
JSON Schema 语义匹配 tool_calls
# 1. 定义工具 @tool def get_weather(city: str) -> str: """获取城市天气""" return f"{city}今天晴，25°C" # 2. 绑定工具到 LLM llm_with_tools = llm.bind_tools([get_weather]) # 3. 调用 — LLM 决定是否使用工具 response = llm_with_tools.invoke( "北京天气怎么样？" ) # 4. 检查工具调用请求 if response.tool_calls: for tc in response.tool_calls: print(tc["name"]) # "get_weather" print(tc["args"]) # {"city": "北京"} else: print(response.content) # 直接回答

CONCEPT · 概念解释

先理解：什么是 TypedDict / 类？

📋 比喻：填表格
TypedDict 就像规定好格式的表格：
预先声明"这张表有哪些字段、每个字段是什么类型"，然后填数据时按格式来。
好处：字段少了会报错、类型不对会报错。
对比：普通 dict vs TypedDict
# 普通 dict：可以塞任何东西 state = {"messages": [], "count": 0} # 拼错字段名不会报错 → 埋雷 state["conut"] = 1 # typo # TypedDict：预先声明格式 class AgentState(TypedDict): messages: list count: int # 拼错字段名 → 编辑器立即提示错误
🧱 类 class 是什么？
类 = 自定义的数据类型。
就像 Python 内置了 str、int、list，你也可以用 class 定义自己的类型。

TypedDict、BaseModel 都是特殊的类，负责"规定数据格式"。

✓ 本课要求：能读懂类定义，理解每个字段的作用即可，不需要自己从零写类。
🎯 为什么 Agent 需要 TypedDict？
Agent 有很多状态字段（消息、重试次数、路由决策...）。
用 TypedDict 把它们"锁死"：
1 编辑器自动补全字段名
2 拼错会立即报错
3 团队协作时字段清晰
4 LangGraph 强制要求这种格式
✋ 学两周 Python 的你只需要
看到 class AgentState(TypedDict) → 就想"这是一张规定格式的表格"；看到冒号后面的类型 → 就想"这是这个字段该填什么类型"。不需要掌握类继承、方法定义等 OOP 概念。
Speaker Notes
核心要点
  • 初学者最怕的两个词：class 和 TypedDict
  • 用"规定格式的表格"比喻，避开继承、方法等 OOP 概念

生产级 AgentState
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    original_query: str
    rewritten_query: str
    retrieval_attempts: int
    guardrail_result: dict
    routing_decision: str
    sources: list
    relevant_sources: list
    grading_results: list

关键字段说明
messages：带 reducer 的消息列表
retrieval_attempts：重试计数器
guardrail_result：安全检查结果
routing_decision：路由决策记录
sources：检索到的文档列表

add_messages reducer

记忆存储机制详解
  • Checkpoint 机制：MemorySaver 的核心是 Checkpoint（检查点）。每次 Agent 执行后，会将当前状态（messages 列表 + 中间变量）序列化为一个 checkpoint 对象，存储在内存字典中
  • 存储结构：内部维护 self.storage: dict[thread_id, list[checkpoint]]，每个 thread_id 对应一个 checkpoint 列表，按执行顺序追加
  • thread_id 隔离：不同 thread_id 的数据完全隔离，互不可见。切换 thread_id 等于切换对话频道
  • 读取流程：每次 invoke() 时，Agent 先从 storage 中读取该 thread_id 的最新 checkpoint，恢复 messages 历史，再将新的用户消息追加到历史中，送入 LLM
  • 写入流程：LLM 响应后，Agent 将新的 AI 消息 + tool 调用结果追加到 messages，生成新 checkpoint，写回 storage
  • 内存 vs 持久化：MemorySaver 存在进程内存，重启即丢失。生产环境使用 SqliteSaver（SQLite 文件）或 PostgresSaver（数据库），接口完全一致，只需替换 checkpointer 参数
代码讲解
  • from langchain.checkpoint import MemorySaver
  • memory = MemorySaver() — 初始化空存储
  • agent = create_agent(llm, tools, checkpointer=memory)
  • 调用时传入 config={"configurable": {"thread_id": "session-1"}}
  • 同一 thread_id 的调用会自动读取历史 checkpoint 并共享上下文
  • 不同 thread_id 之间完全隔离，互不干扰

常见问题

  • Q: 如何持久化？A: 使用 SqliteSaver 或 PostgresSaver，代码只需替换 checkpointer
  • Q: 记忆会无限增长吗？A: 是的，messages 会累积。可通过 trim_messages 或自定义 reducer 裁剪

会话记忆 MemorySaver

记忆如何存储？
Checkpoint 机制：每次 invoke() 后，Agent 将完整状态（messages 列表 + 中间变量）序列化为 checkpoint，存入内存字典。
内部结构：storage[thread_id] = [checkpoint_1, checkpoint_2, ...]
读写流程
  • 读取：invoke 时先查 storage[thread_id] 最新 checkpoint，恢复历史 messages
  • 追加：新用户消息追加到历史 messages 尾部
  • 执行：LLM 处理完整 messages，可能调用工具
  • 写入：AI 回复 + 工具结果追加为新 checkpoint
thread_id 会话隔离
不同 thread_id = 不同对话频道，数据完全隔离。
切换 thread_id 等于开始新对话，旧上下文不可见。
多用户：每用户分配不同 thread_id 即可并发对话。
内存 vs 持久化
MemorySaver → 进程内存，重启丢失
SqliteSaver → SQLite 文件，重启不丢
PostgresSaver → 数据库，多进程共享
接口一致，只需替换 checkpointer 参数

先理解:同步 vs 异步(async/await)

☕ 比喻：等外卖
同步：点外卖后站在门口等，30 分钟啥也干不了。

代码对比
# 同步：等 LLM 全部回完再显示 response = llm.invoke("你好") print(response) # 等 5 秒后一次性显示 # 异步：LLM 边生成边显示（打字机效果） async def chat(): async for chunk in llm.astream("你好"): print(chunk, end="") # 一个字一个字显示
🔑 三个关键字
async def
→ "这个函数是异步的"（可以边等边干）

await
→ "等一下这里，等好了继续"

async for
→ "循环处理陆续到达的结果"（如 stream）
🎯 Agent 为什么需要异步？
1. 流式输出：LLM 边生成边展示（打字机）
2. 并发调用：一次调多个工具，节省时间
3. 用户体验：不阻塞，界面不卡
4. 生产标配：几乎所有 Agent 框架都用异步
✋ 你只需要记住
看到 async def → 前面加 async；看到 await → 记得整个函数必须是 async def；看到 async for → 用来接收流式结果。不需要掌握 event loop、协程调度等底层细节。

流式输出实现原理
  • 底层机制：LLM API（如 DashScope/OpenAI）原生支持 SSE（Server-Sent Events）流式协议。请求时设置 stream=True，服务端逐 token 返回，每个 token 作为一个 SSE event
  • LangChain 封装：astream() 底层调用 LLM 的流式接口，将 SSE event 转换为 Python AsyncIterator，每个 chunk 包含一个或多个 token
  • Agent 层面：create_agent 基于 LangGraph 构建。LangGraph 的 astream() 会流式输出图执行过程中每个节点的中间结果
  • stream_mode 区别："messages" 流式输出 LLM 的每个 token（最细粒度）；"values" 每个节点执行完后输出完整状态；"updates" 仅输出状态的增量变更
  • chunk 结构：stream_mode="messages" 时，chunk 是一个元组 (message_chunk, metadata)，message_chunk.content 是文本片段，metadata["langgraph_node"] 标识来源节点
  • 工具调用流式：当 Agent 决定调用工具时，工具调用参数也是流式返回的（tool_call_chunks），但实际工具执行结果是一次性返回的
代码讲解
  • async for chunk in agent.astream(...) — 异步迭代每个流式块
  • stream_mode="messages" — 获取 token 级别的细粒度流
  • chunk[0].content — 当前 token 的文本片段
  • chunk[1]["langgraph_node"] — 元数据，判断是 agent 节点还是 tools 节点
  • print(..., end="", flush=True) — 无换行立即刷新输出，实现逐字效果
  • 也可用 stream_mode="updates" 按步骤获取，适合日志场景

流式输出 astream()

流式如何实现？
底层：LLM API 原生支持 SSE 协议，请求设 stream=True，服务端逐 token 返回。
LangChain：将 SSE event 转为 AsyncIterator，每个 chunk = 1 个 token 片段。

stream_mode 三种模式

  • "values" — 每节点完成后输出完整状态

chunk 结构
stream_mode="messages" 时：
chunk = (message_chunk, metadata)
chunk[0].content → 文本片段
chunk[1]["langgraph_node"] → 来源节点
工具调用参数也流式返回，但执行结果一次性返回

  • 非流式：⏳ 3秒后显示完整回答
  • 流式：⚡ 首字 < 500ms，逐字显示

import os, asyncio from langchain_openai import ChatOpenAI from langchain_core.tools import tool from langchain.agents import create_agent from langchain.checkpoint import MemorySaver # ── 1. 定义工具 ── @tool def get_weather(city: str) -> str: """获取指定城市的天气信息。args: city — 城市名称""" weather_map = {"北京": "晴 25°C", "上海": "多云 28°C", "广州": "雷阵雨 30°C"} return weather_map.get(city, f"暂无{city}的天气数据") # ── 2. 创建 LLM ── llm = ChatOpenAI( model="qwen-plus", api_key=os.environ["DASHSCOPE_API_KEY"], openai_api_base="https://dashscope.aliyuncs.com/compatible-mode/v1", temperature=0, ) # ── 3. 创建 Agent（带记忆）── agent = create_agent(llm, tools=[get_weather], checkpointer=MemorySaver()) config = {"configurable": {"thread_id": "demo"}} # ── 4. 流式交互 ── async def main(): async for chunk in agent.astream( {"messages": [{"role": "user", "content": "北京和上海天气如何？"}]}, config=config, stream_mode="messages", ): if chunk[1]["langgraph_node"] == "agent" and chunk[0].content: print(chunk[0].content, end="", flush=True) asyncio.run(main()) # → Agent 自动调用 get_weather("北京") 和 get_weather("上海")，流式输出综合回答

PART 3 · 生产实践

Guardrail：Agent 的第一道防线

什么是 Guardrail？
Agent 执行任务前的输入校验节点。判断查询是否在 Agent 的领域范围内，过滤无关请求，节省资源。
Guardrail 工作流
1 用户输入到达 Agent
2 LLM 对查询打分 (0-100)
3 score ≥ threshold → 继续执行
4 score < threshold → 路由到 out_of_scope
5 礼貌拒绝 + 引导用户回到领域
Guardrail 评分示例
class GuardrailScoring(BaseModel): score: int # 0-100 reasoning: str # 示例查询评分 "帮我查今天的天气" → score: 95 ✓ "今天股票怎么样" → score: 30 ✗ "写一首诗" → score: 10 ✗ "arXiv上有哪些新论文" → score: 88 ✓
生产价值
节省成本：过滤无关查询，不浪费 LLM 调用
提升体验：快速拒绝比错误回答更好
安全合规：防止越狱和恶意输入
可追踪：记录拒绝原因用于优化
与 Module 2/4 的关联
Guardrail 是 Module 2 LangGraph 条件路由的经典案例，也是 Module 4 Agentic RAG 的第一个节点。这里先建立概念，后面会看到完整实现。
Speaker Notes
核心要点
  • Guardrail 是生产 Agent 的标配——没有它，Agent 会处理各种无关查询
  • 评分使用 LLM 完成，temperature=0 确保一致性
  • threshold 通常设为 50-70，根据业务调整
  • out_of_scope 节点要"礼貌拒绝"而非"报错"
  • 这是 Agent 安全的第一课，后面还有输出过滤等
