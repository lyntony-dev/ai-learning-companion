PROBLEM · 痛点分析

单 Agent 的局限性

能力瓶颈
单个 Agent 的 Prompt 上下文有限，当任务需要多种不同专业能力时，一个 Agent 难以兼顾。

例：研究 + 写作 + 审校 三种能力难以在一个 Prompt 中表达
工具爆炸
工具数量增多时，LLM 选错工具的概率上升。bind_tools() 绑定 10+ 工具后准确率显著下降。

例：搜索、摘要、翻译、写作、审校、格式化… 全绑一个 Agent
无法并行
单 Agent 是串行执行的。当任务有独立子任务时，无法并行处理，效率受限。

例：同时搜索 3 个不同主题的资料，单 Agent 只能一个个查
单 Agent → 能力有限 · 工具冲突 · 串行瓶颈 → 需要多 Agent 协作

核心概念
  • LangGraph 是 LangChain 团队推出的图式编排框架
  • 核心思想：把 Agent 工作流建模为有向图
  • 节点 = 函数/Agent，边 = 数据流向
  • 条件边 = 根据状态动态选择下一个节点
  • 状态 = 在节点间传递的共享数据结构
类比讲解
可以类比为工厂流水线：每个工位（节点）负责一道工序，物料（状态）在工位间传递，质检环节（条件边）决定物料送去哪个工位。
CORE CONCEPT

什么是 LangGraph？

定义
LangGraph 是一个基于有向图的 Agent 编排框架，把复杂任务拆解为多个节点，通过边和条件路由组织执行流程，实现多 Agent 协作。
与 LangChain 的关系
  • LangChain 提供单 Agent 能力（LLM + Tools）
  • LangGraph 提供多 Agent 编排能力
  • LangGraph 中的节点可以是 LangChain Agent
  • 两者是互补关系，不是替代

四大核心概念
  • State（状态）：TypedDict 定义，在节点间传递
  • Node（节点）：Python 函数，接收 state 返回更新
  • Edge（边）：固定连接，A 执行完一定走 B
  • Conditional Edge（条件边）：根据 state 动态选路
代码预告
这页是概念铺垫，后面每一页会逐一展开。先让学生有整体印象，不急于写代码。
FUNDAMENTALS · 核心概念

图的四大核心概念

① State · 状态
在节点间传递的共享数据结构，通常用 TypedDict 或 Pydantic Model 定义。

每个节点接收当前 State，返回需要更新的字段，LangGraph 自动合并。
② Node · 节点
一个 Python 函数，接收 State 作为参数，返回一个 dict 更新 State。

节点可以是：Agent、工具函数、LLM 调用、或任意 Python 逻辑。
③ Edge · 边
固定连接，表示「A 执行完后，一定执行 B」。

graph.add_edge("node_a", "node_b")

适合确定性的执行流程。
④ Conditional Edge · 条件边
动态路由：根据当前 State 决定下一个执行的节点。

graph.add_conditional_edges("node_a", router_fn, {path1: "node_b", path2: "node_c"})

这是实现智能决策的关键。

讲解要点
  • State 是 LangGraph 的核心，一切围绕 State 转
  • TypedDict 是 Python 标准库的类型工具
  • Annotated[list, add_messages] 是 LangGraph 的消息合并策略

易错点
学生经常忘记用 Annotated，直接写 messages: list，导致消息被覆盖而非追加。务必强调 add_messages reducer 的作用。
STEP 01 · STATE

定义状态 State

什么是 State？
State 是在图中流转的共享数据。每个节点读取 State、修改 State，LangGraph 负责在节点间传递和合并。
Reducer 合并策略
  • 默认：返回值直接覆盖字段
  • add_messages：消息列表追加
  • operator.add：列表追加合并
  • 自定义 reducer：任意合并逻辑
from typing import Annotated, TypedDict from langgraph.graph import MessagesState from langchain_core.messages import BaseMessage # 方式一：继承 MessagesState（内置 messages 字段） class AgentState(MessagesState): # messages 已自动包含，带 add_messages reducer next_agent: str # 下一个要执行的 Agent research_data: str # 研究收集到的资料 draft: str # 写作 Agent 的初稿 review_notes: str # 审校 Agent 的反馈 # 方式二：从头定义（手动加 Annotated） class CustomState(TypedDict): messages: Annotated[list[BaseMessage], add_messages] topic: str result: str

STEP 02 · NODE

定义节点 Node

节点的本质
节点就是一个普通 Python 函数：

def node_name(state: AgentState) -> dict:

接收当前 State，返回一个 dict，LangGraph 会自动合并到 State 中。
返回值规则
  • 只返回需要更新的字段
  • 未返回的字段保持不变
  • 带 reducer 的字段按策略合并
  • 可以用 Command 同时更新+路由
from langgraph.types import Command # 基本节点：返回状态更新 def research_node(state: AgentState) -> dict: # 调用 Research Agent 执行搜索 result = research_agent.invoke(state["messages"]) return { "messages": [result], # 追加消息 "research_data": result.content, "next_agent": "writer", # 设置路由 } # 使用 Command 同时更新+路由 def review_node(state: AgentState) -> Command: review = reviewer_agent.invoke(state["messages"]) if "通过" in review.content: return Command(update={"review_notes": review.content}, goto="END") else: return Command(update={"review_notes": review.content}, goto="writer") # 打回重写

STEP 03 · EDGE & ROUTING

边与条件路由

普通边 — 固定连接
graph.add_edge("node_a", "node_b")

A 执行完一定走 B，适合确定性流程。
条件边 — 动态路由
graph.add_conditional_edges(
  "source_node", # 源节点
  router_function, # 路由函数
  {"key1": "node_b", "key2": "node_c"} # 路径映射
)

路由函数根据 State 返回 key，决定下一步。
# 路由函数：根据 state 决定下一个节点 def should_continue(state: AgentState) -> str: # 检查是否已有研究资料 if not state.get("research_data"): return "research" # 需要搜索 # 检查是否已有初稿 if not state.get("draft"): return "writer" # 需要写作 # 检查审校是否通过 if "通过" in state.get("review_notes", ""): return "END" # 完成 else: return "writer" # 打回重写 # 注册条件边 graph.add_conditional_edges( "supervisor", should_continue, { "research": "research_node", "writer": "writer_node", "END": END, } )

完整流程
  • 三步走：创建 StateGraph → 添加节点和边 → 编译
  • compile() 会做校验，确保图结构合法
  • 编译后得到的是可执行的 Runnable，支持 invoke/stream
  • checkpointer 用于持久化状态，支持断点续跑
注意事项
必须设置 entry_point（通过 add_edge(START, "node")）和至少一个到 END 的路径，否则 compile 会报错。

Supervisor 模式详解
  • Supervisor 是最常用的多 Agent 模式
  • Supervisor 本身是一个 LLM，通过 Prompt 让它选择调用哪个 Agent
  • 使用 Command(goto="agent_name") 进行路由
  • 每个子 Agent 完成后返回 Supervisor，由它决定下一步
代码重点
注意 Command 的用法：它同时包含 update（状态更新）和 goto（路由目标）。这是 LangGraph 较新的 API，比 add_conditional_edges 更简洁。
PATTERN 01 · SUPERVISOR

Supervisor 主管模式实现

工作流程
① 用户消息 → Supervisor
② Supervisor 决策：调用哪个 Agent？
③ 被选中的 Agent 执行并返回结果
④ 结果回到 Supervisor
⑤ Supervisor 决策：完成 or 调用下一个
Supervisor 的 Prompt
"你是一个团队主管。根据用户请求，选择合适的团队成员来处理。可选成员：research（资料搜集）、writer（撰写）、reviewer（审校）。"
from langgraph.types import Command from langchain_core.messages import HumanMessage # Supervisor 节点 def supervisor_node(state: AgentState) -> Command: # 用 LLM 决策下一步 response = llm.invoke([ SystemMessage(content=SUPERVISOR_PROMPT), *state["messages"], ]) # 解析 LLM 输出，得到目标 Agent next_agent = parse_agent_name(response.content) if next_agent == "FINISH": return Command(goto=END, update={"next_agent": "FINISH"}) else: return Command(goto=next_agent, update={"next_agent": next_agent}) # 子 Agent 节点（执行后回到 Supervisor） def research_node(state: AgentState) -> Command: result = research_agent.invoke(state["messages"]) return Command( update={"messages": [result]}, goto="supervisor" # 完成后回到 Supervisor ) # 构建图 builder = StateGraph(AgentState) builder.add_node("supervisor", supervisor_node) builder.add_node("research", research_node) builder.add_node("writer", writer_node) builder.add_edge(START, "supervisor") graph = builder.compile()

为什么需要循环？
单次检索可能返回不相关文档。让 Agent 自我判断文档质量，自动重写查询，是生产级系统的核心能力。
关键实现
条件边：add_conditional_edges 路由

# LangGraph 循环工作流 graph = StateGraph(AgentState) graph.add_node("retrieve", retrieve_node) graph.add_node("grade", grade_documents_node) graph.add_node("rewrite", rewrite_query_node) graph.add_node("generate", generate_answer_node) graph.add_edge("retrieve", "grade") # 条件路由：相关→生成，不相关→重写 graph.add_conditional_edges( "grade", decide_to_generate, {"generate": "generate", "rewrite": "rewrite"} ) # 重写后回到检索（形成循环） graph.add_edge("rewrite", "retrieve")
Speaker Notes
核心要点
  • 循环工作流是 LangGraph 区别于简单链式调用的核心能力
  • 必须有明确的退出条件，防止无限循环
  • retrieve → grade → rewrite → retrieve 是最经典的 RAG 循环
  • GradeDocuments 使用 structured output 确保判断一致性
  • 查询重写的 temperature 设为 0.3，保持专注但允许变化

PART 3 · 高级模式

Context 依赖注入：生产级 Agent 架构

问题：全局变量的陷阱
传统写法：LLM 客户端、检索器、追踪器作为全局变量。
→ 无法测试（测试环境 LLM 不同）
→ 无法配置（切换模型需改代码）
→ 无法追踪（每个节点手动传 callback）
方案：Context 注入
LangGraph 的 Context 对象在图编译时注入依赖。
→ 节点函数通过参数接收依赖
→ 测试时注入 Mock 对象
→ 生产时注入真实客户端
→ 追踪器自动应用到所有节点
# 定义 Context 类型 from dataclasses import dataclass @dataclass class GraphContext: llm: BaseChatModel retriever: HybridRetriever langfuse: Langfuse max_attempts: int = 3 # 节点通过 Context 接收依赖 async def retrieve_node( state: AgentState, *, context: GraphContext ) -> AgentState: docs = await context.retriever.search( state["rewritten_query"] ) # Langfuse 自动追踪 context.langfuse.trace( name="retrieve", input=state["rewritten_query"], output=docs ) return {"sources": docs} # 编译时注入依赖 app = graph.compile( context=GraphContext( llm=get_llm(), retriever=get_retriever(), langfuse=get_langfuse() ) )
生产实践建议
测试：注入 Mock LLM + Mock Retriever，验证节点逻辑
多环境：Dev 注入小模型，Prod 注入大模型
追踪：Langfuse CallbackHandler 通过 Context 传播
配置：max_attempts 等参数通过 Context 传递
Speaker Notes
核心要点
  • Context 是 LangGraph 0.2+ 的新特性，解决依赖管理问题
  • 比全局变量更安全、更可测试、更可配置
  • 生产系统的 LLM 客户端、追踪器、配置都应通过 Context 注入
  • 测试时注入 Mock 对象是最佳实践
对比传统方式
传统 LangChain Agent 通过全局变量或闭包传递依赖。Context 模式更接近 Spring Framework 的依赖注入理念，是工程化的进步。

from langgraph.graph import StateGraph, START, END from langgraph.types import Command from langgraph.checkpoint.memory import MemorySaver # ─── Supervisor 节点 ─── def supervisor_node(state: AgentState) -> Command: response = llm.invoke([ SystemMessage(content="你是团队主管。根据当前状态选择下一步：" "research（需要搜集资料）、writer（需要撰写）、" "reviewer（需要审校）、FINISH（任务完成）。" "只回复一个单词。"), *state["messages"], ]) choice = response.content.strip().lower() if choice == "finish": return Command(goto=END, update={"next_agent": "FINISH"}) return Command(goto=choice, update={"next_agent": choice}) # ─── 子 Agent 节点 ─── def research_node(state: AgentState) -> Command: result = research_agent.invoke({"messages": state["messages"]}) return Command(update={"messages": result["messages"], "research_data": result["messages"][-1].content}, goto="supervisor") def writer_node(state: AgentState) -> Command: result = writer_agent.invoke({"messages": state["messages"]}) return Command(update={"messages": result["messages"], "draft": result["messages"][-1].content}, goto="supervisor") def reviewer_node(state: AgentState) -> Command: result = reviewer_agent.invoke({"messages": state["messages"]}) review = result["messages"][-1].content return Command(update={"messages": result["messages"], "review_notes": review}, goto="supervisor") # ─── 构建图 ─── builder = StateGraph(AgentState) builder.add_node("supervisor", supervisor_node) builder.add_node("research", research_node) builder.add_node("writer", writer_node) builder.add_node("reviewer", reviewer_node) builder.add_edge(START, "supervisor") graph = builder.compile(checkpointer=MemorySaver()) # ─── 执行 ─── result = graph.invoke( {"messages": [HumanMessage(content="写一篇关于 AI Agent 发展现状的研究报告")]}, config={"configurable": {"thread_id": "report-001"}, "recursion_limit": 50} )

from typing import TypedDict, Literal, Optional from langchain_core.messages import SystemMessage, HumanMessage from langchain_openai import ChatOpenAI import ast, json llm = ChatOpenAI(model="gpt-4o", temperature=0) # ─── 状态定义 ─── class GradingState(TypedDict): submission: str # 学生提交内容 assignment_type: Literal["code", "text"] # 作业类型 rubric: list[str] # 评分点列表 semantic_score: optional[float] # 语义评分 code_score: optional[dict] # 代码检测结果 feedback: str # 最终反馈 # ─── Understand Agent：理解题意，提取评分点 ─── def understand_node(state: GradingState) -> dict: prompt = f"""分析以下学生提交，提取评分要点。 作业内容: {state['submission'][:500]} 返回 JSON: {{"type": "code"|"text", "rubric": ["要点1", ...]}}""" resp = llm.invoke([HumanMessage(content=prompt)]) result = json.loads(resp.content) return {"assignment_type": result["type"], "rubric": result["rubric"]} # ─── Semantic Agent：语义评分 ─── def semantic_node(state: GradingState) -> dict: rubric_str = "\n".join(enumerate(state["rubric"], 1)) prompt = f"""按评分点逐一打分(0-10分)。 评分点: {rubric_str} 学生提交: {state['submission']} 返回 JSON: {{"total": 85.0, "details": [{{"point": "...", "score": 8, "comment": "..."}}]}}""" resp = llm.invoke([HumanMessage(content=prompt)]) result = json.loads(resp.content) return {"semantic_score": result["total"]} # ─── CodeCheck Agent：代码检测 ─── def codecheck_node(state: GradingState) -> dict: code = state["submission"] # 1. 语法检查 try: ast.parse(code) syntax_ok = True except SyntaxError as e: syntax_ok = False # 2. LLM 检查代码规范与逻辑 prompt = f"""检查代码质量，评分维度： 1.正确性 2.可读性 3.边界处理 代码: {code[:800]} 返回 JSON: {{"score": 75, "issues": ["问题1", ...]}}""" resp = llm.invoke([HumanMessage(content=prompt)]) result = json.loads(resp.content) result["syntax_ok"] = syntax_ok return {"code_score": result}

Supervisor 路由与图构建

# ─── Supervisor 节点：分析作业类型 ─── def supervisor_node(state: GradingState) -> dict: # 由 Understand 节点已提取 assignment_type return {} # 仅作为路由中转 # ─── 条件路由：按作业类型分流 ─── def route_by_type(state: GradingState) -> str: if state.get("assignment_type") == "code": return "codecheck" # 编程题 → 代码检测 return "feedback" # 文本题 → 直接生成反馈 # ─── Feedback Agent：汇总评分，生成反馈 ─── def feedback_node(state: GradingState) -> dict: parts = [f"语义评分: {state.get('semantic_score', 0)}/100"] if state.get("code_score"): cs = state["code_score"] parts.append(f"代码评分: {cs['score']}/100") if not cs.get("syntax_ok", True): parts.append("⚠️ 存在语法错误") if cs.get("issues"): parts.append("问题: " + "; ".join(cs["issues"][:3])) prompt = f"""你是教师，根据以下评分信息写反馈。 {chr(10).join(parts)} 学生提交: {state['submission'][:400]} 要求：肯定优点 + 指出不足 + 给出改进建议，200字以内。""" resp = llm.invoke([HumanMessage(content=prompt)]) return {"feedback": resp.content} # ─── 构建图 ─── builder = StateGraph(GradingState) builder.add_node("supervisor", supervisor_node) builder.add_node("understand", understand_node) builder.add_node("semantic", semantic_node) builder.add_node("codecheck", codecheck_node) builder.add_node("feedback", feedback_node) # 线性：START → understand → supervisor → semantic builder.add_edge(START, "understand") builder.add_edge("understand", "supervisor") builder.add_edge("supervisor", "semantic") # 条件路由：semantic 之后按作业类型分流 builder.add_conditional_edges( "semantic", route_by_type, {"codecheck": "codecheck", "feedback": "feedback"} ) builder.add_edge("codecheck", "feedback") builder.add_edge("feedback", END) graph = builder.compile() # ─── 执行 ─── result = graph.invoke({ "submission": "def factorial(n):\n if n <= 1: return 1\n return n * factorial(n-1)", "assignment_type": "code", "rubric": [] })

Agent vs LangGraph：何时用什么？

维度 LangChain Agent LangGraph StateGraph
适用场景 单 Agent + 多工具 多节点工作流 + 条件路由
工具数量 1-5 个工具 不限（按节点组织）
执行模式 线性：思考→调用→观察→思考 图结构：可循环、可并行
状态管理 对话历史（messages） 自定义 TypedDict（任意字段）
退出条件 LLM 自行决定停止 显式条件边 + max_attempts
可调试性 中等（callback 日志） 高（节点级 trace + Langfuse）
学习曲线 低（几行代码启动） 中（需理解图、状态、边）
生产就绪 中等 高（Context DI + tracing）
选 Agent Executor 当…
✓ 工具少且简单（天气、计算器）
✓ 不需要循环或复杂路由
✓ 快速原型验证
✓ 单轮对话即可解决
选 LangGraph 当…
✓ 需要条件路由（guardrail、评分）
✓ 需要循环重试（查询重写）
✓ 多 Agent 协作（Supervisor 模式）
✓ 需要 Human-in-the-Loop
✓ 生产级可追踪、可测试
Speaker Notes
决策建议
  • 简单场景不要过度设计——Agent Executor 够用就用
  • 一旦需要"判断后路由"或"循环重试"，就该上 LangGraph
  • 生产系统推荐 LangGraph，因为可追踪性和可测试性更好
  • 两者不是互斥的——LangGraph 节点内部可以调用 Agent

ADVANCED · 人机协作

Human-in-the-Loop

什么是 HITL？
在图执行过程中暂停，等待人工输入后再继续。

适用于：
  • 高风险决策（如发送邮件、执行交易）
  • 内容安全审核
  • 需要人工确认的关键步骤
  • 人工修正 Agent 输出
核心 API
  • interrupt(value) — 暂停执行，返回 value 给调用者
  • Command(resume=value) — 恢复执行，传入人工输入
  • 需要 checkpointer 来保存暂停时的状态
from langgraph.types import interrupt, Command # 在 Writer 节点后加入人工审核 def human_review_node(state: AgentState) -> Command: # 暂停图执行，展示初稿给人工审阅 draft = state.get("draft", "") human_feedback = interrupt({ "question": "请审阅以下报告初稿：", "draft": draft[:500] + "...", }) # 人工反馈写入 state if human_feedback.get("approved"): return Command( update={"review_notes": "人工审核通过"}, goto="supervisor" ) else: return Command( update={"review_notes": human_feedback.get("comment", "需要修改")}, goto="writer" # 打回重写 ) # 调用方式 # 第一次调用会被 interrupt 暂停 result = graph.invoke(initial_input, config) # 人工审阅后恢复执行 result = graph.invoke( Command(resume={"approved": True}), config # 同一个 thread_id )
